# Phase 0–8 architecture decisions

The product source of truth is `REMI_Codex_Spec.md`. Phase 2 adds target discovery and the storage adapter. Phase 3 wires the persisted creation wizard and atomic first-version activation. Phase 4 adds the schedule producer and delivery fan-out. Phase 5 adds the delivery worker, per-unit progress, retry/recovery and private History.

## Boundaries and persistence

- Domain is independent of grammY and PostgreSQL. A schedule context snapshots the version timezone and explicitly selects `gregorian`.
- Rule definitions contain no runtime counters. `ScheduleCursor` owns `consumed_count`, `next_due_at`, and mutable execution state.
- Immutable versions own ordered content references, rules and targets; operational pause/delete and execution progress stay separate. Phase 3 adds reminder/version/cursor tables and persisted drafts/sessions. Phase 4 adds executions, contributing rule links and deliveries; Phase 5 adds delivery item progress and its content mapping.
- `pg` + reviewed SQL is the lightweight alternative allowed by Spec §43.4. Migrations are transactional, serialize via a transaction advisory lock, verify SHA-256 checksums and reject unknown history. Startup requires the exact migration set.
- All persisted timestamps use `TIMESTAMPTZ`; pool sessions use UTC. PostgreSQL BIGINT values remain strings in JavaScript.
- Logs contain controlled event codes only; raw Telegram updates/errors, message bodies, connection strings and tokens are not serialized.

## Recurrence contract

`nextOccurrence(rule, after, context, consumedCount)` returns a canonical UTC instant **strictly after** the input, or `null` on exhaustion. `nextOccurrences` simulates future committed scheduled occurrences for preview only. It has no side effects. `preview` merges the rules, orders by instant and deduplicates exact timestamps while preserving every contributing rule ID. Disabled rules are excluded. Distinct minutes remain distinct executions.

Creation validation is separate from persisted-rule validation: `validateNewRule` rejects past/equal one-time dates relative to an explicitly injected clock. Existing one-time definitions remain readable after they expire. All JSON variants reject unknown fields and validate actual Gregorian dates, positive integer intervals and end conditions. The internal interval/count validation cap is 10,000; preview requests are bounded to 1,000 entries. These are internal resource guards, not new UI features.

Weekdays use ISO Monday=1 through Sunday=7. Weeks start Monday. Anchor date is an inclusive lower bound and fixes cycle parity; weekdays earlier than the anchor within its first week do not run. Monthly arithmetic advances from the first day of the anchor month, then selects the requested day or weekday. Missing dates skip, never clamp. Yearly February 29 skips invalid years, including non-leap centuries. Calendar search jumps to the relevant period rather than replaying every day since creation. An impossible monthly cycle returns null after checking a complete Gregorian cycle. Dates outside Temporal's supported range raise a range error rather than silently truncating a schedule.

All custom intervals use elapsed time: hour=3,600 seconds, day=86,400 seconds, week=604,800 seconds. Calendar daily/weekly rules preserve local wall time instead. This explicitly resolves the interval-vs-calendar distinction in Spec §7.6.

## DST and date boundaries

Temporal `compatible` disambiguation selects the earlier instant in a repeated local time and shifts a nonexistent time forward by the size of the timezone gap. It produces at most one occurrence for an overlap. The next normal day returns to the configured local wall time. Full-day gaps that collapse two local dates to the same instant collapse to one timestamp as well.

`UNTIL_DATE.at` is an inclusive UTC instant. `endOfLocalDate(date, zone)` provides the last nanosecond before the following local day; it does not assume all days last 24 hours. Formatters/parsers must convert user date choices explicitly. Persian/Arabic digit normalization lives in UI code, not recurrence. Jalali recurrence is deferred.

## Counters and scheduler integration

`consumedCount` means committed scheduled executions attributed to this rule, irrespective of delivery success or target count. Skipped/paused dates and manual runs do not increment it. Preview simulates increments but never writes them. Two contributing rules each consume one occurrence even when their shared timestamp dedupes to one execution.

Resume calls `nextOccurrence` with the original rule and the resume instant, retaining the actual consumed count. New-version cursors begin at the activation boundary; to include a timestamp exactly at `effective_at`, pass `effective_at - 1ns` to this strictly-after API. Execution creation, contributing-rule links and counter advancement must be one DB transaction in Phase 4. Preview dedupe is not a substitute for DB uniqueness or delivery idempotency.

Phase 4 implements missed-run policies. Phase 5 cancels unstarted inactive-version executions at claim and lets started executions finish their original package. Phase 6 adds atomic replacement-version activation and the management UI, with persisted pause/resume and race tests. Phase 3 implements atomic first-version activation.

## Phase 2: targets

Infrastructure membership/migration handlers run before the private owner gate; control commands and callbacks remain behind it. New targets require a membership event performed by the configured owner. Changes to known targets are accepted regardless of which administrator performed them. Private chats and the configured Storage are excluded. `/targets` paginates ten rows, hides chat IDs and offers explicit per-page refresh. Icons summarize reachability and permission to send at least one supported content type; later package selection must call `Targets.revalidate(id, kinds)` with every required type.

The permission snapshot records individual text/media rights. Group membership alone does not imply all media permissions. Channel posting and pin permissions are separate. A transient validation error does not deactivate a known target; explicit removal or permanent forbidden/chat-not-found does. Initial discovery can use the membership event with conservative permissions if getChat fails. Subsequent successful revalidation refreshes defaults.

Group migration retains the old row as a redirect (`migrated_to_id`) and atomically creates/reuses the new target. No history/reference is deleted, including when the new chat was discovered first. Future selection/delivery code must resolve old IDs through `Targets.resolve`; the registry lists only canonical rows. Late events for old chat IDs cannot reactivate redirect rows. Owner row locks serialize migration transactions, and queries remain owner scoped.

## Phase 2: storage and capture contract

`ContentCapture.archiveUnit(messages)` accepts one standalone owner-private message or one complete album (2–10 items). Phase 3 calls this adapter only during the explicit persisted content-capture step. Telegram provides no album-complete event or expected album length. The adapter cannot infer an omitted third album item from two supplied messages.

An album is sorted by source message ID and copied with one `copyMessages` call. Standalone messages use `copyMessage`. Mixing unrelated messages, album IDs or incompatible album media kinds is rejected before copying. The adapter keeps metadata, file IDs, canonical message IDs and unit order; no download/upload or file bytes enter the filesystem/DB. Version content items refer to `(archive_id, archive_position)`; the archive ID identifies a contiguous album unit. An edited source creates a new archive fingerprint; an unchanged source may reuse an existing archive.

Before copy, a unique owner-scoped SHA-256 fingerprint claims a durable `COPYING` intent. Simultaneous/replayed requests cannot both send. Exactly matching successful copy results and all item references commit atomically to `READY`. Telegram may skip uncopyable messages in [copyMessages](https://core.telegram.org/bots/api#copymessages); a shortened response is therefore `UNKNOWN`, never guessed into an incorrect source-to-storage mapping. Known copied IDs remain available for later reconciliation. The adapter never edits canonical messages or deletes orphans.

Timeouts, 5xx and persistence failure after copy are handled conservatively: no automatic archive retry. A process crash can leave `COPYING`; it is treated as an uncertain outcome on replay. Clear 4xx rejection becomes `REJECTED` (429 reports a temporary failure). Rejected inputs receive Persian error results and cannot mutate previous successful archives. A new message sent by the owner is a new capture request. Phase 5 implements a separate destination delivery retry queue; the archive adapter makes no exactly-once delivery claim.

Storage verification requires a private channel/supergroup, no public usernames, no content protection, present membership and permissions for the requested media types. Startup verifies all V1 content types without posting a probe; capture verifies its own requested types again. Protected/unsupported incoming content is rejected. Reachability/permission checks cannot guarantee a later Telegram copy succeeds, so the copy result remains authoritative.

Migration 002 requires UTF8 to support Persian text; migration 001 is unchanged. Phase 2 adds no production or development dependency. Tests use fake Bot API calls and a separately installed, temporary PostgreSQL runtime.

## Phase 3: creation wizard

`CreationWizard` is the application state machine. Telegram handlers translate commands/messages/callbacks into inputs and render returned views. Persian rule-form parsing is separate from the domain recurrence engine. Every transition operates on a persisted `wizard_sessions` row and its `reminder_drafts` JSON payload; strict rule validation runs before activation. No active version is mutated during input collection.

States are NAME → CONTENT → RULE_TYPE → RULE_FIELDS → RULE_REVIEW → RULE_LIST → TARGETS → PREVIEW. Conditional fields implement all six rule primitives, including monthly day/nth-weekday branches and per-rule end conditions. One-time has no recurrence/end questions. Preview uses the same recurrence merge/dedupe engine and shows up to five valid future instants. Rules with no remaining future occurrence are rejected at confirmation. The first version snapshots the draft timezone and defaults to LATEST_ONLY.

Each owner has at most one ACTIVE session. `/new` resumes it; `/cancel` marks only its session/draft inactive. Sessions expire after 24 hours; successful field/button transitions refresh expiry. Content receipt is persisted without bumping revision so a displayed Done button remains usable across album updates. Callback data carries a short session token, revision, action and small option index; target IDs remain in server-side state. Both owner context and revision are checked; stale/forged choices cannot mutate another session. `(owner, Telegram update_id)` receipts and owner row locks make replayed updates and concurrent confirmation idempotent. A failed reply after DB commit can be recovered through `/new`; delivery of UI replies is not transactional with PostgreSQL.

Incoming capture payloads are whitelisted Telegram metadata, never media bytes. Draft pending messages survive restart. On explicit Done, album groups have a 1.5-second quiet period after their last received item. The wizard then archives units in source-message order; one album stays contiguous. Additional items from that album do not generate redundant receipt messages. Telegram's lack of a completion marker means the user must wait for their upload to finish; the quiet period is a heuristic, not an exactly-complete guarantee. Failed units stop subsequent archiving to preserve order, retain prior successful units, and require explicit removal/resubmission. Late media after CONTENT is rejected with a friendly message rather than interpreted as a form response.

Wizard transitions use a short-lived PostgreSQL transaction and an owner `FOR NO KEY UPDATE` lock. Done can hold that lock while sequential Telegram copy operations run; this intentionally serializes this personal bot's wizard. Archive intents/results commit independently on the pool so an interrupted wizard save can replay a READY archive without another copy. NO KEY UPDATE permits foreign-key inserts referencing that user on the archive connection. This is not a general distributed workflow engine; capture is bounded to 100 messages. Slow Telegram calls delay this owner's next transition. The single polling consumer remains required.

Confirmation rechecks all selected target permissions for the actual content types. The transaction independently verifies archive ownership/READY state, target ownership/reachability, rule validity and session revision/expiry. It creates REMInder, Version 1, ordered content references, rules, target links and zero-count cursors, activates the version, points current_version to it and deactivates the draft/session as one commit. Initial cursors use the effective instant minus one nanosecond with the strict-after recurrence API. PostgreSQL triggers protect activated definition fields and version children, while runtime cursors remain mutable. A composite FK prevents a reminder from pointing to another reminder's version.

Migration 003 is additive; 001 and 002 are unchanged. Safety bounds currently limit names to 100 characters, content to 100 messages, rules/targets to 20 each. Long previews are split into Telegram-sized messages, with action buttons on the final message. Phase 6 reuses this draft workflow for active reminder editing. No new dependency was introduced.

## Phase 4: scheduler producer

`planDue` is a pure domain function using the existing strict-after recurrence engine. `PgScheduleProducer.tick(now)` supplies one fixed instant per batch and commits each reminder separately. Up to 25 reminders are claimed per tick. The application loop awaits completion before waiting `SCHEDULER_POLL_MS`; it catches failures with a controlled event code and retries on the next tick. Shutdown interrupts idle wait, drains the in-flight tick, then closes the pool. No Telegram API calls occur inside production transactions. Readiness still measures polling and DB connectivity, not end-to-end delivery progress.

The claim query joins the current activated, unretired version of an ACTIVE reminder and checks for enabled due cursors. `FOR UPDATE OF r SKIP LOCKED` serializes each reminder while allowing other reminders to progress. The transaction then locks all its enabled due cursors in stable ID order. Claiming individual cursors with SKIP LOCKED would allow two producers to split overlapping rules and expose a partially attributed execution, so the reminder is the claim unit. All future pause/resume/version-change writers must acquire the same reminder lock before cursor/version changes; locked reminder → cursors is the shared lock order.

All planned rule instants are canonicalized, merged by exact time and sorted. Each distinct instant creates one scheduled execution, every contributing rule link, and one PENDING delivery for every immutable version target. Unreachable targets are retained for the delivery worker to report/revalidate rather than silently omitted. Version target IDs and positions are the snapshot; later group migration resolution follows the existing target redirect contract. Composite foreign keys prevent cross-version execution/rule references. A unique `(version, scheduled_for)` partial index and unique dedupe key independently prevent duplicate scheduled executions; manual executions use their own keys. SQL timestamp strings preserve PostgreSQL microseconds instead of passing through JavaScript Date milliseconds. Wizard schedules are minute-aligned.

Cursor updates and count consumption commit with these rows. Only generated occurrences consume counts; each overlapping rule consumes one, independent of target count or delivery success. `last_due_at` records the latest generated instant, not skipped dates. Exhausted cursors become inactive with null next_due_at. Before-commit failures roll back everything; after-commit restart sees advanced cursors. An unexpected uniqueness conflict with an unadvanced cursor indicates damaged/reset runtime state and fails closed; it never blindly consumes counts twice or attaches late contributors to a running execution.

The Spec gives minute precision but does not define the lateness boundary. Phase 4 explicitly treats the current UTC minute up through `now` as on-time; earlier minute occurrences are missed. This avoids SKIP discarding every normal occurrence merely because polling is a few seconds late. SKIP jumps to the current minute without consuming skipped counts. LATEST_ONLY selects the last due occurrence **per rule**, then merges exact overlaps across rules. A bounded binary search over instants uses the same recurrence engine to find that last instant without walking decades of outage. UNTIL_DATE still bounds the candidate; skipped dates do not consume AFTER_N_EXECUTIONS.

CATCH_UP emits oldest-first up to `MAX_CATCH_UP_EXECUTIONS_PER_RULE` (default 10, supported 1–1000). If more due dates remain, the cursor retains its next backlog instant with `active=false` and `blocked_reason=CATCH_UP_LIMIT`. This hold is persistent across ticks/restarts; simply limiting each tick would eventually flood all backlog. The loop logs `scheduler.catch_up_blocked`. There is no automated unblock or manual backlog replay UI. Phase 6 supports explicitly discarding the backlog through pause/resume: pause cancels pending scheduled executions, and resume rebases cursors strictly after the resume instant. A count-exhausted rule has no backlog and is not held.

Paused/deleted reminders, retired/noncurrent/unactivated versions, disabled rules and inactive cursors cannot produce. Phase 6 resume rebases cursors strictly after the resume instant with original anchors and existing counts under the reminder lock. The producer creates no new work for old versions; the management lifecycle cancels unstarted executions while preserving started delivery progress.

Migration 004 is additive; prior migrations are unchanged. Main starts the producer after polling starts. Phase 4 originally left deliveries PENDING; Phase 5 now consumes that persisted queue using its original immutable versions.

## Phase 5: delivery ownership and recovery

`DeliveryWorker` orchestrates a repository session and a Telegram transport. `PgDeliveryRepository` claims pending/due retry deliveries and recoverable PROCESSING rows. Claim preparation is transactional with reminder → execution → delivery row lock order and `FOR UPDATE OF d SKIP LOCKED`. Each worker also holds a PostgreSQL **session advisory lock** keyed by delivery ID on one checked-out connection for the entire delivery. This lock spans committed item writes and network calls without holding a database transaction across Telegram calls. Other workers cannot treat a live sender as abandoned. This requires a direct database connection or session pooling, not PgBouncer transaction pooling. No lease expiry, heartbeat service or Redis was added.

On first claim, immutable ordered content references become persisted delivery units. A standalone message is one unit; a contiguous archive album is one unit with a relational mapping to all its content items. Repeated references to the same archive start a new unit when archive positions restart. Materialization and PROCESSING transition commit together. Each unit records canonical storage IDs, kinds, sequence, attempt count, destination chat, result IDs and a controlled error code. Only this operational progress changes; canonical archive messages and version content remain untouched.

The worker revalidates the remaining content types against the owner-scoped target registry and resolves migration redirects before sending. The resolved target and title are recorded on the delivery. If two version target references converge on the same migrated target, execution-row serialization reserves that target once; the duplicate delivery is cancelled with MERGED_TARGET, without making a successful aggregate look failed. A permanent copy rejection indicating unavailable target marks its resolved registry row unreachable. Content-specific permission denial remains a delivery failure without incorrectly removing permissions for unrelated content kinds.

Before every copy, SENDING and the incremented attempt count commit. Only then does the transport call `copyMessage` for a standalone item or `copyMessages` for one album (2–10 items, increasing canonical IDs). The explicit unit boundary is the Spec's per-item recovery option; separate messages are not batched together. No transformation, download or upload happens. The copy request has a 30-second abort deadline. A complete, unique positive message-ID response is required for SENT; partial IDs are retained on UNKNOWN but never guessed into a success mapping. This follows the [copyMessages skip behavior](https://core.telegram.org/bots/api#copymessages), checked 2026-10-03.

After connection/process loss, PostgreSQL releases the advisory lock. Recovery of an orphan SENDING unit marks it and its delivery UNKNOWN and sends nothing. If the last SENT write committed and the process stopped between units, recovery skips all SENT units and resumes the suffix. A database error recording a successful copy escapes the send-error classifier: the durable SENDING intent remains, so the next claim resolves it as UNKNOWN instead of resending. An old worker whose DB connection died cannot commit another SENDING intent. Exactly-once external delivery is not claimed; even a crash immediately after SENDING but before the actual request can conservatively become UNKNOWN.

## Phase 5: retries, concurrency and History

Explicit Telegram 429 errors preserve [retry_after](https://core.telegram.org/bots/api#responseparameters) as a minimum wait. Explicit Telegram 5xx errors retry with exponential delay (1 second base, 5 minute cap), plus 0–249ms jitter. A larger retry_after is never clipped to the cap. Preflight network failures are safe to retry because no send started. A generic network/timeout failure during copy is ambiguous and becomes UNKNOWN; there is no blind transport retry. Permanent rejection, partial copy response and UNKNOWN stop the remaining package. Default maximum is five attempts per unit; bounded configuration supports 1–100. Preflight failures also have a delivery-attempt ceiling. Retry timestamps and attempts survive restart, and already SENT units never consume another send attempt.

Delivery concurrency defaults to two (bounded 1–8); each loop awaits one delivery and sleeps one second when no work is available. A package is serial. The target queue keeps newer executions behind an older pending/processing/retry delivery with the same target ID, preserving catch-up order. Terminal failures and UNKNOWN do not block later scheduled executions. Migration deduplication is per execution; general global rate limiting and fairness across migrated aliases are not implemented. Main reserves `DELIVERY_CONCURRENCY + 6` pool connections for delivery, Daily Header, the polling lock and UI/preflight/producer capacity. Shutdown stops polling and producer, drains active workers, releases the polling lock and then closes the pool.

Delivery completion/failure and execution aggregation happen in one transaction under the execution row lock, preventing concurrent target results from publishing a stale aggregate. Remaining pending/processing/retry targets keep PROCESSING; all successful targets (ignoring merged aliases) yield SUCCEEDED; any successful target or SENT prefix alongside failure yields PARTIAL_FAILED; otherwise FAILED. A delivery with an uncertain outcome remains explicitly UNKNOWN in History, even though execution states have no UNKNOWN variant. An unstarted deleted/noncurrent-version execution is cancelled at claim; a paused reminder cancels scheduled work but still permits explicitly confirmed manual work. Once PROCESSING, its original immutable version continues.

`/history` is registered behind the private owner gate and before the wizard's generic message handler. PostgreSQL applies owner scoping to every page and optional reminder filter. Pages show five executions, immutable version names/timezones, scheduled/manual kind, aggregate state, ordered per-target outcomes, sent/total unit counts, safe error summaries and next retry time. Version IDs/numbers are retained internally without exposing implementation jargon in normal UI. Long messages are split; navigation callbacks contain only a reminder ID/page and stay under Telegram's 64-byte limit. Queries remain read-only. Manual retry/reconciliation of UNKNOWN is deferred as allowed by the Spec; neither History nor restart automatically resends it.

Migration 005 is additive and introduces no package dependency. Starting this version processes any existing Phase 4 pending queue. Validation uses a real PostgreSQL server and fake Bot API responses, including concurrency and injected crash boundaries; live Telegram delivery, real network interruption, Docker and Darkube deployment have not been exercised.

## Phase 6: management and immutable edits

`/reminders` is registered behind the private owner gate, before the generic wizard handler. Ten-row pages show active/paused reminders and next due times. The detail menu provides edit, private content preview, pause/resume, confirmed manual run, paused duplicate, History and confirmed soft delete. Callback data carries reminder ID and operational revision (under 64 bytes); every mutation rechecks ownership, deletion and revision inside its transaction. `(owner, Telegram update_id)` receipts make replay inert, while row locking plus revision changes reject double taps from separate updates. Manual and delete confirmation use clearly labeled confirmation screens; old confirmations cannot act on a newly saved definition.

Lifecycle transactions lock owner with NO KEY UPDATE, then reminder, then affected executions/cursors. Workers and producer share the reminder lock as their lifecycle serialization boundary. Pause deactivates current cursors and cancels only PENDING scheduled executions/deliveries. Resume keeps original rule definitions/anchors and actual consumed counts, seeks strictly after the resume instant, and clears catch-up holds because the user explicitly elects to skip the paused period. It does not create a version. Confirmed manual run snapshots the current version and targets with a unique manual key, makes no rule links/cursor changes, and is allowed while PAUSED. Delete marks DELETED, deactivates cursors, cancels all unstarted work and retains history/storage. PROCESSING executions are untouched in all cases.

Duplicate atomically creates a distinct PAUSED reminder, Version 1 with a bounded copy name, new content/rule IDs referencing the existing canonical archives, copied target/settings definitions and zero-count inactive cursors. There are no copied executions, history, delivery results or old versions. Resume later computes future times. Already expired one-time rules can remain in a paused copy for editing; they do not become a fresh scheduled occurrence merely because the reminder was duplicated.

The existing persisted wizard now supports EDIT_REMINDER sessions with a database FK to the base reminder/version. Starting an edit copies ordered archive units, rules, enabled flags, counts for display, targets, timezone and missed policy into an isolated draft. One owner still has one active draft; starting another operation does not silently discard it. Save locks the reminder, checks the persisted base identity/current version/deletion and independently validates actual archive ownership and target permissions. It assembles new children, retires the old definition, deactivates its cursors, cancels only unstarted old executions, activates the replacement and swaps the reminder pointer in one commit. Failure rolls back all of these effects. The active/paused operational status is preserved, including a pause that happened while the draft was open.

Rule IDs are fresh per version. Because the Spec does not explicitly prescribe count migration for an unchanged rule, Phase 6 chooses continuity: matching original rule ID and structurally equal config carry the **live count read under the save lock**, not the stale preview count. Toggle, name/content/target/policy changes therefore do not replenish count-limited rules. Edited/new/duplicated rules start at zero. Existing exhausted or expired rules remain valid definitions; enabled new/changed rules require a future occurrence. Disabled/exhausted rules produce no active cursor. New-version cursor times start at the activation boundary. An unchanged catch-up hold remains held across edits; deliberate pause/resume is the supported way to discard that backlog. Preview counts are a draft snapshot and may differ by a scheduled occurrence that commits before Save.

The rule editor preloads all six rule forms and offers keeping each current value; add/remove/duplicate/toggle only mutate the draft. Timezone and missed-policy changes are also draft edits. Content edits reuse immutable capture: append, remove, move a unit up/down, or replace after successful archival. The text/caption edit UX explicitly asks for the corrected message (or full album) to be resent; it is implemented as canonical replacement rather than editing any old Telegram message. Albums remain contiguous units and are not split/merged. Failed replacements retain the old reference and persist their failure for explicit removal/resubmission. Replacement capacity accounts for the outgoing unit at the 100-item cap. Ten-unit content pages keep keyboards bounded.

Private preview commits an update receipt before copying any current content to the authenticated owner's private chat. It creates no execution/delivery rows and touches no counters or configured targets. A failed/ambiguous preview is not retried automatically; a fresh explicit preview is a new user action. It uses the existing copy-unit transport. Manual retry/reconciliation of UNKNOWN and storage GC remain deferred.

Migration 006 adds operational reminder revisions, edit-session base references and management update receipts; previous migration files remain unchanged. No dependency was added. Tests cover real DB lifecycle transactions, rollback on failed activation, concurrent saves/producer, manual replay and concurrency, live count carry-forward, paused duplicates, deletion/history preservation and completion of an old processing execution after save/delete. Telegram UI/copy calls remain simulated; production credentials and deployment are not configured here.

## Phase 7: reliability validation and diagnostics

Tests terminate the actual PostgreSQL backend holding a delivery advisory lock at SENDING and SENT boundaries. A fresh worker recovers UNKNOWN without replay in the former case and sends only the remaining unit in the latter. Existing suites retain coverage for partial album responses, 429 retry timestamps, attempt limits, permission loss isolated by target, producer races, activation rollback and persisted wizard restart. Delivery events now carry controlled internal delivery/execution/reminder/target IDs, without chat IDs, message bodies or raw errors. A failing logging sink cannot interrupt a committed send transition.

## Phase 8: independent Daily Header

Migration 007 adds configs, daily runs, persisted drafts and input receipts; earlier migrations are untouched. `/daily` is registered behind the private owner gate. One config per owner/chat selects an owner-private destination or an existing group/supergroup/channel target; private chats never enter ordinary reminder targets. New config creation also checks migrated target ancestors to avoid creating a second config for the same resolved group. Changes use a draft with 24-hour expiry, short token/revision callbacks, per-update receipts and final Save. An existing reminder draft and a Daily Header draft cannot be edited through the UI at the same time. Cancel leaves committed settings intact. Config revisions reject stale pause/resume/edit actions.

`headerDay` is pure and uses the existing Temporal dependency with compatible DST disambiguation. It computes today's local date and the next local wall-clock boundary; it never enumerates downtime days. Newly saved configs can send today when the selected time has already passed, while explicit resume skips elapsed time. Gregorian Persian-language formatting lives separately in `ui/fa/daily-header.ts`. A unique `(config_id, local_date)` receipt survives settings changes and restarts.

The worker holds a config session advisory lock; UI writers try the same transaction advisory lock, rejecting a change while a send is in progress. Short transactions atomically advance due time with receipt creation and replace the previous-pin pointer with pin progress. Telegram calls are outside transactions. Send commits SENDING first, then records its positive message ID before pin. Interrupted/ambiguous sends become UNKNOWN with no automatic resend; a known 429/5xx send rejection retries within the current date and configured attempt cap. Preflight permission checks and pin/unpin have separate retry stages. Known successful sends are never repeated just because pin or unpin failed. Expired-day work is cancelled rather than pinning old dates after downtime.

Pin order is new own message first, previous recorded own message second. Both previous message ID and its chat are snapshotted; unpin always includes that explicit ID and never calls `unpinAllChatMessages`. Configs retain the last successfully recorded pin; send-only or pause does not remove it. A permanent pin/unpin error appears in the recent five results. If pin succeeds but its DB write fails, the explicit pin can safely repeat. A long outage or permanent failure can leave an old own pin behind; no destructive reconciliation is attempted. Text delivery is not claimed to be exactly once. Manual UNKNOWN retry, arbitrary templates, Jalali display and storage GC remain deferred.

Group/channel send and pin rights are checked before confirmation/enable and each daily send. The [Telegram pin and unpin contract](https://core.telegram.org/bots/api#pinchatmessage), checked 2026-10-03, allows private non-service message pinning and requires group `can_pin_messages` or channel `can_edit_messages`. Permission failure leaves a clear daily outcome and does not stop unrelated configs.

## Minimal Darkube path requested by the owner

The deployment scope is Dockerfile + `darkube.json` + four required variables + a short [quickstart](darkube-quickstart.md). No extra service, web panel or deployment framework was added. `HEALTH_PORT` overrides `PORT`; absent both, port 3000 is used. Pre-deploy migrations are explicit and transactional. The bot stays on one replica and is not a sleeping/serverless service.

An application-wide session advisory lock keyed by bot ID serializes long polling during Darkube's old/new overlap. A new initialized instance is healthy while awaiting the lock so Darkube can retire the old one without a readiness deadlock. Losing the lock connection initiates shutdown; normal shutdown drains workers before releasing it. Direct PostgreSQL/session pooling is required. This coordinates deployments using the same DB, not unrelated copies with the same token against other databases. First upgrade from a build without this lock requires stopping that old copy. Docker image execution and live Darkube/Telegram smoke tests remain unperformed in this environment.
